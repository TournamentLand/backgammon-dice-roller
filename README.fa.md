# backgammon-dice-roller

[English](README.md) | فارسی

فرمول تاس‌ریزی قابل‌اثبات (provably-fair) مبتنی بر HMAC برای تخته‌نرد آنلاین.

این همان کدی است که در نسخه‌ی نهایی (production) برای تولید و اعتبارسنجی
تاس‌های میزهای تخته‌نرد [Tournament Land](https://tournamentland.com) استفاده
می‌شود. این کد به‌صورت مستقل و جدا منتشر شده تا:

- هر کسی بتواند دقیقاً ببیند یک تاس چگونه تولید می‌شود — بدون ابهام و بدون نیاز به «به ما اعتماد کن»
- هر کسی بتواند به‌طور مستقل تاس‌های هر مسابقه‌ی فاش‌شده را دوباره محاسبه و بررسی کند،
  بدون نیاز به وب‌سایت ما، سرور ما، یا حتی اتصال اینترنت
- کد سمت کلاینت و سمت سرور بازی، هر دو مستقیماً از همین پکیج استفاده می‌کنند
  (نه یک پیاده‌سازی دستی و جداگانه)، پس چیزی که اینجا منتشر شده دقیقاً همان چیزی
  است که در حال اجراست، نه یک نسخه‌ی مشابه

## مشکلی که این پروژه حل می‌کند

یک سرور تخته‌نرد، در اصل، می‌تواند به‌جای مقادیر تصادفی، مقادیری «به‌نفع خودش»
انتخاب کند. استفاده از یک CSPRNG خوب در سمت سرور (که کد نسخه‌ی نهایی این پروژه
پیش از وجود این طرح نیز از آن استفاده می‌کرد) از بایاس *آماری* جلوگیری می‌کند،
اما همچنان از بازیکنان می‌خواهد که فقط به حرف سرور اعتماد کنند.

این طرح در عوض هر تاس را **پس از اتمام بازی، قابل‌بررسیِ مستقل** می‌کند؛ با
همان الگوی commit-reveal که بازی‌های تاس در کازینوهای کریپتویی شناخته‌شده
استفاده می‌کنند:

1. پیش از شروع مسابقه، سرور یک `serverSeed` مخفی تولید می‌کند و
   `sha256(serverSeed)` — یعنی **تعهد (commitment)** — را برای هر دو بازیکن
   منتشر می‌کند. هیچ‌کدام از بازیکنان هنوز خود مقدار را ندیده‌اند، اما هش آن
   از همین لحظه ثبت شده است.
2. کلاینت هر بازیکن یک `clientSeed` تصادفی در مرورگر خودش (نه در سرور) تولید
   کرده و آن را ارسال می‌کند. سرور نمی‌تواند این مقدار را پیش‌بینی یا انتخاب کند.
3. هر تاس با ترکیب `serverSeed`، هر دو `clientSeed` و یک `nonce` افزایشی
   (یکی برای هر تاس) از طریق HMAC-SHA256 محاسبه می‌شود، سپس بایت‌های حاصل با
   روش rejection sampling (در ادامه توضیح داده شده) به مقادیر ۱ تا ۶ نگاشت
   می‌شوند تا از بایاس ناشی از باقی‌مانده‌گیری (modulo) جلوگیری شود.
4. وقتی مسابقه تمام شد، سرور `serverSeed` را فاش می‌کند. از این پس هر کسی
   می‌تواند:
   - تأیید کند که `sha256(serverSeed)` با همان تعهدی که *پیش از* شروع مسابقه
     منتشر شده مطابقت دارد (پس سرور نمی‌توانسته پس از دیدن روند مسابقه، seed
     دیگری انتخاب کند)، و
   - تک‌تک تاس‌ها را از روی seedهای فاش‌شده دوباره محاسبه کند و مطمئن شود که
     دقیقاً با چیزی که در طول مسابقه نمایش داده و بازی شده مطابقت دارد.

از آنجا که HMAC-SHA256 یک تابع شبه‌تصادفی (pseudorandom function) است، هیچ
راه محاسباتی امکان‌پذیری برای سرور وجود ندارد که بتواند پس از پایان بازی
یک `serverSeed` پیدا کند که دنباله‌ای از تاس‌های «به‌نفع خودش» را بازتولید
کند — این کار مستلزم شکستن خود HMAC-SHA256 است.

## فرمول

Seedها (`serverSeed`، `clientSeedHost`، `clientSeedGuest`) همیشه رشته‌های
UTF-8 ساده هستند — در عمل رشته‌های hex — که مستقیماً به‌عنوان کلید/پیام HMAC
استفاده می‌شوند، و هرگز جداگانه از hex به بایت خام تبدیل نمی‌شوند. این کار از
ابهام «hex یا بایت خام» برای هر کسی که بخواهد فرمول را دوباره پیاده‌سازی یا
دستی بررسی کند جلوگیری می‌کند.

```
message = `${clientSeedHost}:${clientSeedGuest}:${nonce}`
digest  = HMAC-SHA256(key = serverSeed, message)

برای هر مقدار تاس درخواستی، بایت بعدیِ استفاده‌نشده از digest مصرف می‌شود:
  اگر byte >= 252: رد شود، بایت بعدی گرفته شود   // 252 = 6 × 42
  در غیر این صورت: value = (byte % 6) + 1

اگر digest پیش از تولید مقادیر کافی تمام شود:
  digest = HMAC-SHA256(serverSeed, `${message}:${extraCounter}`)
  extraCounter = 1, 2, 3, ...  (ادامه‌ی مصرف از این digest جدید)
```

**چرا بایت‌های ≥ ۲۵۲ رد می‌شوند؟** یک بایت به‌طور یکنواخت بین ۰ تا ۲۵۵ (۲۵۶
مقدار) قرار دارد. ۲۵۶ بر ۶ بخش‌پذیر نیست، پس صرفاً `byte % 6` کمی به نفع
مقادیر ۰ تا ۳ نسبت به ۴ و ۵ بایاس دارد. ۲۵۲ = ۶ × ۴۲ بزرگ‌ترین مضرب ۶ است که
در یک بایت جا می‌شود، پس با محدود کردن به بایت‌های ۰ تا ۲۵۱ (۲۵۲ مقدار،
دقیقاً ۴۲ عدد برای هر باقی‌مانده) و دور انداختن بقیه، بایاس به‌طور کامل حذف
می‌شود. این همان تکنیکی است که
[`dice_roller` مربوط به Backgammon Galaxy](https://github.com/Backgammon-Galaxy/dice_roller)
استفاده می‌کند (رد کردن بایت‌های ≥ ۲۵۲ پیش از `rem(byte, 6) + 1`)، و همان کاری
است که `crypto.randomInt` در Node.js نیز به‌صورت داخلی انجام می‌دهد.

به ازای هر بار تاس‌ریزی، **یک nonce مصرف می‌شود** — فارغ از این‌که آن
تاس‌ریزی به چند مقدار نیاز دارد؛ تاس شروع بازی (opening die) یک مقدار از
nonce خودش می‌گیرد؛ یک نوبت معمولی دو مقدار از یک nonce می‌گیرد.

## چگونه خودتان یک مسابقه را اعتبارسنجی کنید

لازم نیست به این اعتماد کنید که جاوااسکریپت وب‌سایت ما دست‌نخورده مانده است.
دو راه برای بررسی مستقل وجود دارد:

**در مرورگر، به‌صورت آفلاین:**
```
فایل verify.html را از این ریپازیتوری دانلود کرده و مستقیماً باز کنید (نیازی به سرور نیست).
JSON فاش‌شده‌ی مسابقه (serverSeed، clientSeedHost، clientSeedGuest،
commitmentHash، rollLog) را پیست کرده و روی Verify کلیک کنید.
```

**در خط فرمان:**
```bash
node bin/verify.js --reveal=./match-reveal.json
# یا بررسی دستیِ یک تاس:
node bin/verify.js --serverSeed=<hex> --clientSeedHost=<hex> \
  --clientSeedGuest=<hex> --nonce=0 --count=2
```

## API

```js
const dice = require('backgammon-dice-roller');

dice.commitmentHash(serverSeed);
// => هش hex از sha256، که پیش از شروع مسابقه منتشر می‌شود

dice.deriveValues({ serverSeed, clientSeedHost, clientSeedGuest, nonce, count });
// => [3, 5]  (آرایه‌ای از `count` مقدار، بین ۱ تا ۶)

dice.verifyReveal({ serverSeed, clientSeedHost, clientSeedGuest, commitmentHash, rollLog });
// => { commitmentValid, rolls: [{nonce, count, expected, actual, valid}, ...], allValid }

dice.generateSeedHex(32);
// => یک seed hex تصادفی جدید (crypto.randomBytes در Node / crypto.getRandomValues در مرورگر)
// فقط برای ساختن seed استفاده می‌شود — اعتبارسنجی هرگز به این نیاز ندارد.
```

فایل‌های `src/index.js` و `src/sha256.js` هیچ وابستگی‌ای ندارند و بدون هیچ
تغییری هم در Node، هم در مرورگر روی HTTPS، و هم در مرورگری که یک فایل محلی
را مستقیماً باز کرده اجرا می‌شوند — یک مسیر کد واحد، نه «همان الگوریتم که دوبار
پیاده‌سازی شده و امیدواریم با هم یکی باشند».

## تست‌ها

```bash
npm test
```

شامل تست‌های determinism، تست‌های تشخیص دستکاری (tamper-detection) — که یک
commitment نادرست، یک تاسِ دستکاری‌شده، یا یک seed جابه‌جاشده را تشخیص
می‌دهند — و یک تست chi-square goodness-of-fit روی ۲۰۰٬۰۰۰ تاس‌ریزی که یکنواختیِ
آماریِ توزیع ۱ تا ۶ را تأیید می‌کند — خروجی همین تست هم بخشی از اثبات عمومی
است، چون هرکسی می‌تواند این ریپازیتوری را کلون کرده و خودش اجرا کند.
